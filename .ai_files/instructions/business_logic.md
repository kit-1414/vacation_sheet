  # Бизнес логика проекта

  ## Сущности проекта

  ### Пользователь

  Потльзователь (userAccount)
  человек, который логиниться в систему и выполняет в ней нужные действаия.

  #### Атрибуты пользователя:
  - email  - до 100 символов
    Email — регистронезависимый уникальный идентификатор пользователя.
  - время добавления (задаётся приложением);
  - время редактирования (задаётся приложением);
  - имя - строка до 100 символов;
  - фамилия  - строка до 100 символов.
  - is_admin  - Boolean - признак что пользователь админ
  - is_active - Boolean - признак что пользователь активен.

  ## Проект
  Проект  (Project)- это, Например, проект по разработке продукта.
  он нужен для объединения пользхователей в группы внутри системы. 

  ### Аттрибуты проекта
  Сущность `Project` содержит название, необязательное описание и даты создания и обновления.
  Проекты можно создавать, изменять и удалять.
  Привязка пользователя к проекту выполняется идемпотентным `PUT`, отвязка — `DELETE`.
  Не возвращать JPA-сущности через API; использовать DTO.

  #### Аттрибуты проекта

  - Имя — уникальная регистронезависимая строка. Это необходимо учитывать на экранах создания и редактирования.
    Длина: непустая строка от 1 до 100 символов.
    Валидация: допускаются буквенно-цифровые символы а также "-", "." и "_".

  - Комментарий — любые символы.
    Длина: от 0 до 1000 символов.
    Валидация: любые символы.

  ### Связи Проекта
  Проект имеет 2 связи c пользователями:
  - `Project` связан с `UserAccount` отношением "Участник проекта" (member) many-to-many через таблицу `project_members`".
  - `Project` связан с `UserAccount` вторым отношением "Рководитель проекта" (Manager) many-to-many через таблицу `project_manager`.

  #### Руководители проектов
  Описываем логику связи Руководитель проекта Проекта и пользователя системы -
  Пользователь является руководителем(менеджером), если есть хотя бы 1 проект, где он руководитель. 

  - Данная связь даёт доступ к функциональности руководства проектами (будет описано в документации фронтенда).
  - Назначение пользователя руководителем выполняется аналогично добавлению как участника.
  - Не возвращать JPA-сущности через API; использовать DTO.

  ## Добавление Пользователи при логине
  - При первом успешном OAuth2-входе сохранять пользователя в PostgreSQL: `lower(email)`, имя и фамилию.
  - При последующих входах идентифицировать пользователя по `lower(email)`, но больше ничего не менять.
  - Внешним ключом идентификации служит `lower(email)`.

  ## Пользователи и Роли
  Каждому залогиненому пользовалелю назначается 1..N ролей
  - NOBODY  - user.isActive = false
  - USER    - user.isActive = true
  - MANAGER - user.isActive = true и пользователь является руководителем(менеджером)
  - АDMIN   - user.isActive = true && user.isAdmin = true 
   
   Роль АDMIN дает доступ ко всем страницам и действиям в системе. 
   При любом перечне ролей на разрешение чего либо админдобавляется в этот список по умолчанию.
  
   Если для страницы, списка или ссылки не прописаны явно запреты или правила - они разрешены для любой роли.
   
   Термин "Активен" - в описании экранов встречается термин "активен" для некой роли(ролей).
   Это значит что для упомянутых роле доступен переход или действие, для остальных - тролько текст (или конока неактивна)

   В коде бэкенда роли представлены
     - констнтами - литералами
     - енумом, со свойством roleName т этих литералов

  ## Доступ к текущему пользователю и ролям
  для работы с текущим поьзователем, ролями и тп используем отдельную ДТО b сервис
  и метод CurrentUserService.getCurrentUser(): CurrentUserDto.
  используем этот серсвис и ДТО 
   - в конроллере "*/me"
   - в конроллерах(сервисах), где требуется проверять принадлежность сущьностей текущему пользователю 
     передавая саму ДТО как параметр в сервис

  ### Заявление на отпуск
  Сущьногсть "заявление на отпуск" (vacation_request)

  Заявление на отпуск создается/редактируется пользователем. 
  Далее согласуется(approve) или отклоняется(reject) руководителем.

  #### Аттрибуты заявление на отпуск
  - заголовок (title) - text 50 символов 
  - состояние (request_state)   (enum): Черновик (DRAFT), Готов (READY), Одобренный(APPROVED), Отклоненный(REJECTED)
  - вид отпуска (vacation_type) (enum): Оплачиваемый отпуск (PAYMENT_VACATION), Отпуск за свой счет (FREE_VACATION)
  - дата начала отпуска
  - дата завршения отпуска
  - комментарий пользователя (user_commends) - текст 2000 символов 
  - комментарий руководитеоя manager_comments)- текст 2000 символов

  #### Связи заявление на отпуск
  - связь с создателем-заявителем - пользователем (author_id)- one-to-many. устанавливается при создании
  - связь с руководителем  (manager_id)- one-to-many. Устанавливается по при одобрении - отклонении
  - 
  #### Политика действий (методов на бэке) с заявлением на отпуск
  методы для работы с заявлениями разделены на группы по ролям

  ##### Методы для пользователя
  для методов полтзователя на бэке реализовать отдельные методы
  /user/actions/vacation_request/* - для получения списка заявлений, создания, редактирования, удаления
  для получения списка у сервиса заявлений должен быть метод - VacationRequestService.getRequestsByOwnerId(id): List<VacationRequest> 

  на бэке при действиях с заявлениями по ID - получение, обновление, удаление нужна доп проверка что 
  заявлени принадлежит текущему полтзователю.
  Соотв у сервиса заявлений VacationRequestService должен быть метод проверки авторста заявления
  VacationRequestService.checkIsCreator(requestVacationId, CurrentUserDto): Boolean
  VacationRequestService.failIfNotCreator(requestVacationId, CurrentUserDto) - 
  выкидывает исключение с ошибкой доступа и сообщением в дебаг что попытка доступа к чужому заявлению (на англ)

  Автору (создателю - пользователю) обновлять и удалять заявления можно толоко если заявления в состоянии DRAFT или READY.

  ##### Методы для руководителя
  для методов руководителя на бэке реализовать отдельные методы
  /manager/actions/vacation_request/* - для рассмотрения заявлений

  Операции рассмотрения заявления по ID (выполняются руководитеме проетов)
  реализуются отдельными методамии для рукводител на бэке и не требуют проверки принадлежности заявления пользователю.

  Но требуют проверки состояния - такая операци возможно только с заявлением в разрешенном руководителю состоянии READY, APPROVED, REJECTED
  Метод позволяет сменить состояние из любого на любое  в списке разрешенных  и редактировать комментарий руководителя. 
  Допускается не менять состояние. Только отредактировать комментарий. 
  При переводе состояния в READY связь с руководителем очишается и удаляется комментарий.

  метод рассмотрения заявления:
        передает в path  - "vacationRequestId": <ID заявления>   
        принимают на вход JSON
   {
    "managerComment": <комментарий руководителя>. Допустим NULL
    "updateManagerComment": Boolean - говорит, надо ли обновлять комментарий руководитеоя значением из запроса. при значении = false  не надо 
    "requestState":  <READY | APPROVED | REJECTED> 
   }

  При `updateManagerComment = false` текущее значение комментария руководителя сохраняется.
  При `updateManagerComment = true` комментарий руководителя обновляется значением `managerComment` из запроса.
  Значение `managerComment = NULL` при `updateManagerComment = true` очищает комментарий руководителя.
  При переводе заявления в состояние READY руководитель и его комментарий очищаются независимо от значений
  `managerComment` и `updateManagerComment`.

  Метод получения заявления на рассмотрение по ID:
  - получает `vacationRequestId` в path;
  - возвращает заявление с автором, руководителем и проектами автора по связи `project_members`;
  - не возвращает заявления в состоянии DRAFT.

  Метод получения списка заявлений на рассмотрение - 
  Должен быть реализован отдельный метод получения спсика заявлений на отпуск для руководителя.
  В него не должны попадать заявления с состоянием DRAFT.

  ##### Методы для админа
  для методов админа на бэке реализовать отдельные методы
  /admin/actions/vacation_request/* - для получения списка заявлений, создания, редактирования, удаления.
  Пир реализации нажна проверкка на бэке, что тек пользователь админ.
  Методы админа пока не реализоввывать (без наличия необходимости на бэке)

  ## Действия пользователя в системе

  ### Удаление пользователей и проектов

  - При удалении пользователя удаляются только пользователь и его связи с проектами.
  - При удалении проекта удаляются только проект и его связи с пользователями.

  ## Структура фронтенда

  ### Главное меню

  После входа фронтенд показывает главное верхнее меню. Меню содержит:

  - email текущего пользователя;
  - кнопку выхода пользователя;
  - ссылку на список проектов;
  - ссылку на список пользователей системы.
  - ссылку на страницу личного кабинета пользователя

  #### Работа с пользователями

  Пользователи появляются в системе при входе через Яндекс. Пользователи добавляются двумя способами:

  1. При входе, если пользователя ещё нет в системе, email, имя и фамилия берутся из OAuth-атрибутов.
  1.1. если пользователь первый в  системе, то он становится админом
  1.2 пользователь добавляется isActive=true. 
  2. На странице добавления нового пользователя.

  #### Страница «Список пользователей»
  Доступна к просмотру для любой роли.

  Страница содержит
  - список пользователей системы с атрибутами
  - кнопку перехода на страницу «Добавление пользователя» - активна только для роди ADMIN
  - возможность удалить выбранных пользователей -  активна только для роди ADMIN
  - ссылки на страницы редактирования пользователей - активна только для роди ADMIN

  #### Страница «Добавление пользователя»
  Страница доступна только для роли ADMIN
  Страница добавляет нового пользователя.

  #### Страница «Редактирование пользователя»
  Страница доступна только для роли ADMIN
  Страница позволяет редактировать атрибуты существующего пользователя.

  ### Работа с проектами

  #### Страница "Список проектов"
  Доступна к просмотру для любой роли.
  Страница содержит 
   - список проектов (`Projects`) в виде таблицы
   - возможность удалить выбранные проекты и кнопку создания нового проекта. - активна только для роли ADMIN

  В списке (таблице) показываются атрибуты проектов (и только они):
  - имя
  - время добавления
  - "Команда" в виде числа - кв-во участников проекта
  - «Руководители» в виде числа - кв-во руководителей проекта
  - первые 40 символов комментария;
  - ссылка на страницу редактирования проекта - активна только для роли ADMIN
  - ссылка на страницу «Участники/Руководители проекта» - активна только для роли MANAGER
    Заголовок колонки - текст «Участники/Руководители»
    текст ссылки-кнопки -  «Назначить»

  #### Страница «Создать проект»
  Страница доступна только для роли ADMIN
  Страница позволяет создать новый проект, задав:
  - имя
  - комментарий

  #### Страница «Редактировать проект»
  Страница доступна только для роли ADMIN
  Страница позволяет отредактировать проект, изменив:
  - имя
  - комментарий

  #### Страница «Участники/Руководители проекта»
  Страница доступна для роли Manager
  Страница позволяет добавлять и удалять участников проекта через ссылку в колонке "Команда проекта".
  Страница позволяет добавлять и удалять руководителей проекта через ссылку в колонке «Руководители проекта».
  В списке пользователей необходимо показывать email, имя и фамилию. Список можно сортировать по одной любой колонке и фильтровать по любой колонке с использованием условия `LIKE '%<pattern>%'`.

  ### Страница «Личный кабнет»
  Страница доступна всем
  Содержит информацию о текущем пользователе
 - емайл
 - имя
 - фамилия
 - время добавления в систему
 - время последнего обновления данных о пользоватее
  
  Страница содаржит ссылку на страницу "Заявления на отпуск"  
  Страница содаржит ссылку на страницу "Рассмотрение заявлений на отпуск" - доступна только для роли MANAGER 

  ### Работа с заявлениями на отпуск (создание-редактирование)

  #### Страница «Заявления на отпуск»
  Страница доступна всем
  Страница содержит кнопку "Добавить заявление на опуск" - для создания нового заявления. Активна для роли USER.

  Страница содержит список заявлений на отпуск текущего пользователя в виде таблицы.
  - заголовок
  - время создания
  - состояние запроса
  - тип отпуска
  - ссылку на редактирование заявления. Активна для роли USER. Активна  при состояниях запроса DRAFT и READY
  - кнопка удаления заявления. Активна для роли USER. Активна  при состояниях запроса DRAFT и READY.
   
  Сортировки 
  - по времени создания
  - по дате начала
  - по дате завершения

   Фильтрация
  - по состянию заявления
  - по типу отпуска

  #### Страница «Добавить заявление на опуск»
  Страница доступна для роли USER

  Для заполнения на странице выводятся атрибуты
  - емайл
  - имя автора
  - фамилия автора
  - заголовок
  - дата начала отпуска
  - дата завршения отпуска
  - комментарий автора
  - тип отпуска
  - состояние запроса (доступно к смене состояния)
  - комментарий руководителя - доступно к редактировнию


  #### Страница «Редактировать заявление на опуск»
  Страница доступна для роли USER

  ### Страница «Рассмотрение заявлений на отпуск»
  Страница "Рассмотрение заявлений на отпуск" - доступна только для роли MANAGER
  Страница содержит список всех заявлений на отпукс (с фльтрацией и сортировкой) - исключая сосяние DRAFT
  Страница позволяет укводителю изменить состояние зяаявления (без измемения коммнетария) если это возможно по состоянию заявления.

  Страница содаржит заявления на отпуск пользователей с аттрибутами
  - заголовок
  - емйайл автора (сортировка, фильрация)
  - имя автора (сортировка, фильрация)
  - фамилию автора (сортировка, фильрация)
  - к-во проектоа автора (по связи project_members)
  - время создания (сортировка)
  - дата начала отпуска  (сортировка)
  - дата заврешения отпуска (сортировка)
  - состояние заявления (сортировка, фильрация)
  - тип отпуска
  - ссылку на  смену состояния, если это позволено
  - ссылку на страницу "Рассмотреть заявление на отпуск с комментарием", если доступна смена статуса  

   Сортировки указыны в перечне атрибутов
     
   Фильтрация
    - фильтрация по емайл, имени и фамилии - регистронезависимое вхождение.
    - указана в пеерчне атрибутов
    - по паре дат - интевалу - чтобы отпуск хоть одним днем попадал в заданный интервал. допустим открытый интервал - только с 1 из дат. 
    - по набору проектов- множественный выбор (список всех проектов в системе с чекбоксами). Для фильтрации достаточно пересечения по1 проекту.
   фильтрация состояние при создании страницы имеет выбо - READY  + APPROVED

### Страница «Рассмотреть заявление на отпуск с комментарием»

  а также перечень проектов в которых участвует пользователь

- емйайл имя фамили автора

- время последнего изменения.
- время создания
- дата начала отпуска  - дата заврешения отпуска
- тип отпуска
- состояние заявления (request_state)

Также на стринице выведен список проектов автора заявления (по связи project_members).

  страница позволяет 
   - изменить состояние зхаявления
   - комментарий руководителя
